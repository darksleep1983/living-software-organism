# CLI и работа агентов

LSO по умолчанию работает только для чтения. Его задача - хранить project-owned continuity в понятном виде и давать ограниченную диагностику и evidence восстановления.

Для использования CLI не нужно знать биологическую терминологию.

## Повседневный workflow

Один раз для проекта:

```sh
npm install living-software-organism@0.1.0-rc.3
npx lso init --dry-run
npx lso init --yes
```

Дальше при обычной работе:

1. Агент читает `AGENTS.md`, `.project-corpus/state/PROJECT.md` и `.project-corpus/state/STATUS.md`.
2. Если STATUS указывает активный Task, читается именно этот Task и только нужные ему evidence.
3. Выполняется запрошенное изменение в рамках authority проекта.
4. `lso doctor` или `lso status` используется как свежая проверка согласованности.

Сам LSO **не требует** Task/Report для каждой мелкой правки. Используйте их, когда этого требует локальный протокол или работа существенная, делегированная, рискованная, продолжается между сессиями либо нуждается в долговечной проверке.

## Команды для человека

- `lso doctor [path]`: идентичность проекта, непрерывность, здоровье и evidence восстановления.
- `lso status [path]`: короткий текущий снимок.
- `lso findings [path]`: проблемы и следующие действия, только в режиме предложений.

Добавьте `--json` для стабильного машиночитаемого результата.

## Handoff агенту

`lso context [path] --json` возвращает ограниченные указатели, fingerprints, здоровье и findings. Это индекс к project-owned authority, а не её замена.

Нейтральная к модели последовательность:

```text
context pointers
-> чтение authority проекта
-> ограниченная работа
-> свежая проверка
```

Codex, Claude, Gemini, OpenHands и другие агенты используют тот же поток без provider SDK.

## Evidence восстановления

- `recover plan` описывает известные/отсутствующие inputs и не запускает команды.
- `recover deps` показывает описательные dependency declarations.
- `recover rehearse` копирует объявленную основу в изолированное runtime-хранилище и проверяет её. Live state не восстанавливается.
- `origin verify` - явное сетевое действие для проверки объявленных Git-байтов относительно точного commit.

Проверка исходников не равна восстановлению всей системы. Toolchain, секреты, сервисы, долговечные данные и deployment environment требуют отдельных evidence.

## Конфигурация

`lso.config.json` связывает ID проекта, adapter и ограниченный runtime path. Optional recovery declarations носят описательный характер. Исполняемые команды и значения, похожие на секреты, отвергаются.

Идентичность и текущее состояние остаются в файлах самого проекта, а не дублируются в конфигурацию LSO.

## Обычные и архитектурные названия

Стабильная реализация сохраняет существующие API-имена для совместимости:

| API/термин | Обычный смысл |
|---|---|
| `homeostasis` | Здоровье проекта |
| `repair` | Зафиксированное намерение контролируемого ремонта и проверка |
| `capabilities` | Явная допустимость и привязка возможности |
| `immune` | Проверенные переиспользуемые уроки |
| `metabolism` | Бюджеты ресурсов и наблюдения |
| `history` | История изменений здоровья |
| `recovery` | Готовность восстановления и изолированная репетиция |
| hygiene/autophagy | Только планирование очистки |
| capsule | Ограниченные свидетельства реконструкции |
| trace | Причинная трассировка evidence |
| phenotype | Сравнение объявленных свойств |

Это продвинутая архитектурная терминология. Для повседневного CLI она не обязательна.

## Безопасность

LSO не чинит автоматически, не dispatch'ит работу, не запускает произвольный shell, не работает демоном, не удаляет файлы, не восстанавливает live state, не переключает провайдеров, не списывает деньги и не публикует. `origin verify` - единственный явный сетевой verifier CLI.

Пакет `0.1.0-rc.3` остаётся prerelease. Архитектура остаётся v0.1-v0.7, experimental Organ Systems без версии, Project Corpus Protocol 2.0 с optional Runtime 2.2.0.
